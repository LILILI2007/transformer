# ModLingo 产品与 GitHub 项目策划案

版本：1.0｜日期：2026-10-15｜开发规模：个人｜首发平台：Windows

## 1. 产品定义

ModLingo 帮助普通玩家把星露谷 mod 中已经外置的英语文本变成可使用、可修改、可随版本维护的简体中文翻译包。用户通过中文图形界面完成“选择 mod→配置模型→生成初稿→检查与确认→导出安装”，不需要直接编辑 JSON。

产品承诺是缩短从英文 mod 到可游玩翻译初稿的过程，并减少更新后的重复劳动。不能承诺全游戏通用、任意 mod 一键汉化、人工级质量或格式检查后绝无游戏问题。

长期方向是以独立游戏适配器扩展其他生态，而不是把各种文件中的字符串统一交给模型翻译。第一款游戏明确为星露谷物语。

## 2. 已确认决策

| 决策 | 当前范围 |
|---|---|
| 用户 | 普通玩家为主，可自行修改译文；专业协作后置 |
| 游戏 | 首先支持星露谷物语 |
| 语言 | 首版验收英语→简体中文，数据结构保留扩展可能 |
| 形态 | Windows 优先，本地中文图形工具 |
| 翻译 | 用户自备大模型 API 地址、模型名和密钥，承担调用费用 |
| 更新 | 未变项复用，新增项补译，变更项保留旧译文并确认 |
| 文本入口 | 首版限标准平铺 i18n，不处理硬编码与二进制 |
| 安装 | 仅导出翻译包及引导，不直接覆盖游戏目录 |
| 交付 | 策划案、可运行原型、示例、测试、中文文档及 GitHub 配置 |
| 资源 | 个人开发，没有硬性截止日期，按里程碑推进 |

首版无需账号系统、项目方云后台、收费网关、翻译市场、团队权限或跨游戏兼容层。这些能力没有首版收益证据，不占据核心开发时间。

## 3. 痛点、对象与假设

目标玩家会安装 SMAPI 和 mod，但不熟悉语言文件、API 接口及游戏控制语法。典型任务包括：新 mod 没中文；既有汉化不完整；升级后新增英文；模型把名字译来译去；修改占位符后出现异常；找不到翻译的安装位置。

| 痛点 | 产品处理 | 如何判断解决了 |
|---|---|---|
| 不知道哪里是可译文本 | 校验 manifest 与标准 i18n | 支持与不支持均给出可理解原因 |
| 直接机翻损坏结构 | 只翻译值、遮蔽标记、检查响应 | 损坏候选不能进入有效导出 |
| 原有中文被覆盖 | 现有中文优先保留 | 未变项人工修正不被 API 重写 |
| 更新后重复翻译 | 使用历史原文与键进行差异比较 | 未变项不进入待译队列 |
| 名词不统一 | 项目术语表与复核提示 | 相关术语被发送，缺失时提示 |
| 不会安装或恢复 | 仅翻译 ZIP、身份提示、恢复步骤 | 包内路径明确，原文件不自动修改 |

这些是产品假设，尚未通过玩家访谈验证。没有虚构市场规模、用户数量或满意度数据。下一阶段先邀请 5 名目标玩家做观察式试用，重点观察 API 配置、第一次导出、升级维护；样本小，仅用于发现问题，不用于宣称市场验证。

## 4. 同类工具与选择理由

资料核查截至 2026-10-15，仅核对公开文档，未对同类产品进行完整运行测试。

| 项目 | 已公开能力 | 对本项目的意义 |
|---|---|---|
| [Stardew i18n Translator](https://github.com/Nana1873/stardew-i18n-translator) | Windows 便携应用、标准 i18n、AI 初译、编辑、token 检查、源文变更队列、术语与翻译 ZIP | 与构想高度重合，更新补译不是独创。不得声称其不安全、质量差或维护不足 |
| [Minecraft-Mod-Language-Package](https://github.com/CFPAOrg/Minecraft-Mod-Language-Package) | 社区维护的 Minecraft 模组简中资源包 | 说明现成译文与安装渠道本身有价值，但不直接解决星露谷的输入格式 |
| [xTranslator](https://github.com/MGuffin/xTranslator) | Bethesda 游戏的专用翻译编辑、词典与在线接口 | 说明跨游戏需要结构适配，不能靠通用字符串替换完成 |

新项目成立的理由是构建一个中文优先、依赖少、处理边界可检查、方便个人维护的开源方案。**它目前是待验证的体验与工程取舍，尚未证明比既有工具更好。** 已用同类工具且满意的玩家，不是必须争取的首批用户。

在扩大投入前，必须比较两条路线：继续独立实现，或基于现有项目贡献中文体验和缺陷修复。若真实试用没有发现独立价值，优先贡献现有生态，避免为了完整功能表重复建设。当前原型为独立实现，没有复制同类仓库代码或翻译库。

## 5. 首版范围与分级

### 必须具备

1. 导入单个 mod 文件夹，读取 manifest 的 UniqueID、名称、版本。
2. 接受合法 JSONC 注释、尾逗号和 UTF-8 BOM；拒绝重复键、大小写冲突和非字符串值。
3. 读取 `i18n/default.json`，合并现有 `zh.json`，默认将前者视为英语但提示用户确认。
4. 支持一种 Chat Completions 格式的文本接口，可配置基础地址、模型名、密钥。
5. 分批调用、保护标记、检查响应条目与译文结构，失败保留进度。
6. 人工编辑和确认，维护项目术语，自动保存项目并可迁移副本。
7. 同一 UniqueID 的更新比较：新增、修改、未变、删除分别处理。
8. 导出 UTF-8 中文文件、安装/恢复说明和跳过项报告；不自动修改原 mod。

### 首版明确不包含

- `i18n/default/*.json` 分文件目录和非标准自定义布局。
- 硬编码 `content.json`、DLL、XNB 的提取、反编译和改写。
- 全量事件或对话语法解释器、性别分支自动重写。
- 自动定位全游戏 mod 列表、一键安装、自动回滚。
- 项目方代付 API、用户账号、云端存储、共享译文市场。
- 按键字幕覆盖、OCR、实时游戏画面翻译。

“首版不支持”必须在导入或条目状态中展示，不能在导出后让用户自行发现缺译。标准 i18n 也可能包含复杂脚本，所以支持某类文件不等于支持里面的全部文本。

## 6. 玩家流程

### 初次使用

打开示例体验编辑→选择单个 mod→看到支持范围、现有译文、待译项和暂不支持项→填写 API 配置→测试小请求→确认即将发送的信息及可能费用→批量翻译→集中处理异常→导出→按 UniqueID 安装→进入游戏验证。

API 配置是最大的首次使用门槛之一。首版用中文向导与连接检查降低阻力，后续根据观察结果决定是否增加服务商预设。服务商模型名和价格会变化，不应写死为永久有效，也不假定网页聊天会员包含 API 额度。

### 升级 mod

保留已有项目→载入新版同一 UniqueID 的 mod→逐键对比历史原文→未变项原样保留→新增项进入待译→修改项保留上一版原文与译文，生成新候选并确认→删除项留在历史但不导出→生成新版翻译包。

再次导入同一 mod 会恢复本机已有项目，并按新源文合并。比较依据是源文内容，版本号只作为展示信息；首版不判断语义版本高低，也不能自动分辨用户是否误选旧版本。

### 修改与恢复

玩家保存/确认一条译文后，该条标为人工确认。原文未变化就不被批量翻译覆盖。后续原文改变时仍保留旧值供对照；用户可接受候选、自己改写或清空以回退原文。

安装前复制备份原 `zh.json`；恢复时复制回备份。若原先没有中文文件，删除本次添加的 `zh.json`。原型只给出引导，没有自动备份和恢复按钮。

## 7. 翻译与质量机制

模型负责自然语言表达，程序负责身份、结构、增量和文件写入。每批最多 8 条、约 18000 原文字符；单条超过 16000 字符先跳过。字符数不是 token 数，不能直接换算费用。

处理顺序为：判断支持范围→筛选待译条目→识别并遮蔽支持的控制标记→筛选相关术语→附翻译键作为上下文→调用 API→解析 JSON 响应→校验条目 ID→验证保护标记→还原并检查结构→保存结果。

支持的是保守语法子集，要求占位符/控制符内容、次数和顺序一致，以及换行数量一致。这个限制可能拒绝部分本来可用的语序调整，首版优先结构可靠性。复杂分支、事件和未知语法跳过并列入报告；不能仅凭 token 集合一致宣称游戏逻辑一致。

模型输出与原文完全一致、相关术语缺失或源文发生变化时，集中要求复核。这是确定性规则，不是模型置信度，也不能检测所有语义错误。人名、语气、剧情连贯性仍需人工和实机检查。

译文结构损坏、请求错误尚未处理、变更候选未确认时，阻止整个导出，避免悄悄打包问题。用户可以修正，或清空并保存来选择原文回退。复杂不支持项直接省略；未译项也省略。不能输出空字符串并期待 SMAPI 自动显示英文。

首版上下文以单条文本、翻译键和术语为主，不承诺完整剧情理解。不跨 mod 自动共享译文，避免同词不同语境导致误用。后续可扩展每个 mod 的背景说明、人物设定及相邻对话上下文，但需控制数据发送量。

## 8. 技术架构与仓库

采用 Python 标准库和 Tkinter，以减少个人开发的运行时依赖。`core.py` 不依赖 GUI 或网络，负责 JSONC、项目、增量、检查与导出；`provider.py` 负责接口、批次和保护标记；`gui.py` 负责中文界面、任务调度和保存。

网络请求在后台线程串行执行，UI 线程通过队列接收结果和保存进度。每批结果完成后原子保存；关闭时尚未返回的请求不计入已保存进度。失败不会抹掉已成功批次。

项目存储保留 mod 身份、版本、每键原文/译文、上一版原文/译文、译文所对应源文、来源、待确认状态、错误、归档项和术语。保存位置为 `%LOCALAPPDATA%/ModLingo/projects/`；文件名按 UniqueID 哈希生成，不依赖 mod 文件夹名。

当前数据是单游戏、单目标语言模型；扩展时先升级项目 schema，再添加游戏适配器和 locale 字段。不能把预留扩展理解为现已支持多游戏多语言。

仓库包含源码、原创示例、回归测试、中文文档、MIT 许可证、贡献说明、问题模板、CI 和 Windows 构建脚本。运行无需第三方依赖；构建时独立虚拟环境使用固定版本 PyInstaller，并记录实际构建依赖。

## 9. 数据、成本与开源

本地工作并不表示离线翻译。云 API 会接收待译文本、翻译键和相关术语；本机模型服务可以不离开设备。密钥只存在本次运行内存或用户自行设置的环境变量，不写项目、不进 ZIP、不记原始服务端错误体。HTTPS 用于远程调用，HTTP 仅允许 localhost/loopback，重定向不会携带授权头跟随。

首版无项目方服务器费用和代付额度。用户承担自己的 API 消费；限次重试可能产生额外费用，停止按钮只能停止后续批次。最多尝试三次，请求超时为每次 60 秒，网络较差时当前批次结束可能需要更久。

不提供未经验证的“每个 mod 几分钱”承诺。实际成本应记录输入/输出 token、服务商当前费率、重试和复用比例后计算。未来新增预算限制时，还需要确认服务端 usage 可用性与不同模型计费口径。

工具源码使用 MIT；不打包游戏资产或第三方真实 mod，示例为原创。工具许可不赋予用户转载原 mod 文本的权利；共享翻译包需检查原作者许可。第三方打包组件保留各自许可说明。

## 10. 验收与效果测量

| 验收项 | 方法 | 通过条件 |
|---|---|---|
| 标准文件导入 | JSONC、BOM、重复键及错误值样例 | 合法可读，错误明确拒绝 |
| 原文件保护 | 导入前后字节比较 | 原始 mod 文件没有改动 |
| 结构保护 | 丢失、重复、改序标记及复杂语法样例 | 问题被拦截或明确跳过 |
| 人工修改保留 | 修改→保存→重新打开→更新未变键 | 译文与人工来源保持 |
| 增量正确 | 原版与更新版素材 | 未变项不待译；新增/修改/删除分别处理 |
| API 失败恢复 | 本地 HTTP 服务与失败模拟 | 有界重试、友好错误、成功进度保留 |
| 导出安装 | 检查 ZIP 路径、JSON 和报告 | 只有翻译文件与说明，没有 mod 源码/密钥 |
| GUI 主流程 | 窗口启动、选择、编辑、更新及队列处理 | 无异常，项目可恢复 |
| 真实翻译 | 用户选定 API 和真实标准 i18n mod | 记录质量、复核时间与实际使用成本 |
| 实机显示 | 配套游戏、SMAPI 与目标 mod 版本 | 记录安装、显示和对话结果，不能以单元测试替代 |

当前实现把前八项作为工程验证；真实云端与实机验证单独标记，不假装完成。自动验证详情见 [验证记录](验证记录.md)。

试用阶段关注“从启动到首个可安装包”的总时间，拆分为配置、翻译等待、复核、安装。另记录未变条目复用率、变更漏报、结构问题、术语修改率与失败恢复是否成功。不以单次模型生成速度代表整体体验。

试点目标是：有效标准输入上的未变条目重复调用数为 0、已知结构破坏导出数为 0、人工修改无故丢失数为 0。这些是验收目标，不是对任意真实 mod 的已证实保证。翻译准确率与人工复核量须先制定标注规范再测量。

## 11. 个人开发路线与投入

| 阶段 | 结果 | 当前状态 | 后续参考投入 |
|---|---|---|---|
| M0 范围与证据 | 用户决策、标准入口、同类工具核查 | 已完成 | 根据试用变化维护 |
| M1 可运行原型 | 导入、API、编辑、检查、增量、导出 | 已实现并做工程验证 | 继续修复试用问题 |
| M2 真实试点 | 一个 API、数个许可允许的真实 mod、实机记录 | 未完成 | 约 12–24 小时 |
| M3 普通玩家体验 | 服务预设、错误引导、较大文件性能、用户观察 | 待验证 | 约 20–40 小时 |
| M4 扩大兼容 | 分文件 i18n、语法解析、批量 mod 管理 | 规划 | 约 30–60 小时，依需求排序 |
| M5 发布维护 | 干净机器测试、组件许可、签名评估、版本发布 | 部分构建基础已具备 | 约 12–24 小时及持续维护 |

以上是一个熟悉 Python 与 API 的开发者的粗估区间，不是承诺日期；不包含学习成本或不可预见兼容工作。没有截止日期也应保持小步验证，不能无限扩展后才邀请玩家。

## 12. 风险与推进条件

| 风险 | 当前处理 | 推进条件 |
|---|---|---|
| 与现有项目重合 | 如实列出能力，不宣称首创 | 观察到可验证的中文体验差异再扩大投入 |
| 目标 mod 未外置文本 | 明确拒绝硬编码入口 | 有代表性样本和稳定提取规则再扩展 |
| API 配置劝退 | 中文配置与小额测试 | 观察配置成功率后决定预设或其他模式 |
| 语法覆盖不够 | 保守子集、跳过报告、原文回退 | 每新增语法先增加结构规则和回归素材 |
| 译文流畅但含义错 | 人工编辑、术语提示、实机验证 | 建立逐条质量评审样本 |
| 便携包系统差异 | 提供源码与构建、安排干净机器测试 | 完成目标 Windows 环境测试后公开稳定版 |
| 数据损坏或丢失 | 原子写入、可迁移项目副本、源文件只读 | 后续补滚动备份与迁移测试 |

下一步最有价值的工作是使用真实 API 和一个实际想玩的 mod 做完整验证，而不是立即增加第二款游戏。
